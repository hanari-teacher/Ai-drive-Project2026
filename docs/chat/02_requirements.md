# リアルタイムチャット機能 要件定義書 (`docs/chat/02_requirements.md`)

---

## 1. 目的・利用者・対象範囲・対象外・既存機能との関係

### 1.1. 目的

Express / TypeScript 製の既存Webアプリケーション（TOP / TODO / AI質問アプリ）に、ユーザー同士がリアルタイムでメッセージを送受信できるチャット機能（`/chat`）を追加し、円滑な双方向コミュニケーションを実現する。

### 1.2. 利用者

- **一般ユーザー**: チャット画面（`/chat`）にアクセスし、ユーザー名とコメントを入力してメッセージを送信・閲覧する利用者。
- **管理者**: 一般ユーザーと同様のチャット利用に加え、運用・障害確認・ログ確認等を行う利用者。
- **前提（認証の有無）**: 既存構成情報において認証仕様は未確定のため、本要件定義では認証有無を前提とせず「要確認」とする（セッション単位での人数カウントに用いるセッション識別子・認証連携の扱いは要確認）。

### 1.3. 対象範囲（In Scope）

- `/chat` チャット画面の提供（EJS: `views/chat/index.ejs`）およびクライアント制御（`public/chat/chat.js`）
- `Socket.IO` による同一ルーム（デフォルトルーム）内のリアルタイムメッセージ配信と再接続時の同期
- Neon（PostgreSQL）へのチャットメッセージ保存および最新20件の取得・表示
- デフォルトルームの同時参加人数上限（セッション単位で最大5名、同一ブラウザ複数タブは1名カウント）の制御と、6セッション目以降の満席案内表示および入室・閲覧・投稿の制限（満席表示と `/chat` へのリンク提供）
- マルチインスタンス環境（Vercel等のサーバーレス・複数台構成）を想定した **DB 同期／ポーリング併用** によるメッセージ整合性および全台合計5人制限の確保
- 入力検証（ユーザー名最大50文字、コメント最大500文字、型・前後空白チェック）、通信・DBエラーハンドリング、XSS対策、環境変数による機密情報管理
- `src/apps/chat/`（Router / Controller / Service / Model）および `sql/chat/040_create_chat_messages.sql`、`index.ts` / `local.ts` 統合の要件整理

### 1.4. 対象外（Out of Scope）

- **AIによる自動応答・ボット機能**: 既存AI質問機能との自動連携やAI返信は行わない（ユーザー間コミュニケーション専用）。
- **複数ルーム機能**: 初期スコープはデフォルトルームのみとし、ルーム作成・切替・複数部屋管理は対象外とする。
- **ダイレクトメッセージ（1対1チャット）・既読管理・リアクション・ファイル添付・音声/動画通話**: 初期スコープ外とする。
- **既存機能の仕様変更・改修**: TOP画面、TODO機能、AI質問機能自体の機能追加や仕様変更は行わない。

### 1.5. 既存機能との関係

- **アーキテクチャ踏襲**: 既存TODOアプリ（`src/apps/todo/`）の Router / Controller / Service / Model 分離構成に倣い、`src/apps/chat/` を新設する。
- **インフラ・共通処理の共有**: Neon（PostgreSQL）接続設定（`DATABASE_URL` / `DATABASE_URL_POOLED`）、サーバー起動エントリ（`index.ts` / `local.ts`）、404ハンドリング、グローバルエラーハンドラーと整合させる。
- **非破壊原則**: 既存の TOP、TODO、AI質問、ルーティング、DB接続、404処理、エラー処理の挙動を一切損なわない。

## 3. 画面・リアルタイム送受信・履歴・定員制限の詳細要件

### 3.1. `/chat` 初期表示とユーザー名・コメント入力

- **対象ルーム**: デフォルトルームのみとする。
- **初期表示**: `/chat` にアクセスした際、セッション単位の定員状況を確認し、入室可能であればチャット画面を表示して最新履歴（最大20件）を描画する。
- **入力項目**:
  - **ユーザー名**: 最大 **50文字** の文字列入力。
  - **コメント**: 最大 **500文字** の文字列入力。
- **送信操作**: 送信ボタンクリック（およびフォーム送信操作）によりメッセージを送信する。

### 3.2. 同一ルームへのリアルタイム配信と DB 保存

- **リアルタイム配信**: サーバー側で受理・保存されたメッセージを `Socket.IO` により同一デフォルトルームに参加しているクライアントへ配信し、画面へ追記描画する。
- **DB保存**: 投稿ごとに少なくとも **ユーザー名**・**コメント**・**作成日時** を Neon（PostgreSQL）に保存する。保存成功を基準に配信・履歴反映を行うことで、配信のみ成功してDBに未保存となる不整合を防ぐ。

### 3.3. 初期表示および再接続時の最新20件取得

- **取得件数**: 画面の初期表示時、およびネットワーク瞬断等からの `Socket.IO` 再接続時には、最新 **20件** のメッセージを取得して表示する。
- **順序・重複防止**: 時系列順（古い→新しい、またはUI仕様に沿った一貫した並び順）で描画し、再接続時やポーリングによる同期時に既存表示と重複しないよう制御する（要確認: 20件を超える過去ログの遡り取得／ページネーションの要否）。

### 3.4. 5人参加中の6人目に対する画面表示と入室・閲覧・投稿の制限

- **定員上限と数え方**: デフォルトルームの同時参加人数は **セッション単位で最大5名** とする。**同一ブラウザの複数タブは同一セッションとして1名** と数える。
- **6人目以降の画面表示と再試行導線**: すでに5セッションが参加している状態で6セッション目以降がアクセス・入室しようとした場合、**満席である旨の案内（満席ページ／満席表示）** を表示し、チャット（`/chat`）へのリンクを設置する。
- **入室・閲覧・投稿の制限**: 6セッション目以降に対しては以下をすべて制限する。
  - **入室制限**: ルームへの参加登録・リアルタイム配信ルームへの参加を許可しない。
  - **閲覧制限**: ルーム内のチャット履歴を表示・閲覧させない（満席時に履歴を非表示／未返却とする）。
  - **投稿制限**: メッセージ送信UIを無効化／非表示とし、サーバー側（HTTP API / Socket イベント）でも未入室・満席状態からの投稿を拒否する。

## 4. 入力検証・エラーハンドリング・セキュリティ・回帰確認要件

### 4.1. 入力検証（型・前後空白・文字数超過）

- **型検証**: ユーザー名・コメントが文字列（`string`）であること、必須項目が存在することを検証する。配列・オブジェクト・数値等の不正な型は拒否する。
- **前後空白**: 先頭・末尾の空白（半角スペース、全角スペース、改行・タブ等）をトリムしたうえで空になる場合は不正（空文字と同等）としてエラーとする（要確認: コメント本文の途中の改行を許容するか、文字数カウントをトリム前後どちらで行うか）。
- **文字数超過**:
  - **ユーザー名**: 最大 **50文字**（51文字以上はエラー）。
  - **コメント**: 最大 **500文字**（501文字以上はエラー）。
- **二重検証**: クライアント側（`public/chat/chat.js`）で即座にフィードバックしつつ、サーバー側（Controller / Service）でも必ず検証する。

### 4.2. 通信失敗・DB障害・サーバー例外処理

- **WebSocket通信エラー / 切断**: 接続失敗、タイムアウト、切断発生時は画面にエラー／再接続中等のユーザーフレンドリーな案内を表示する。
- **API通信エラー**: ネットワークエラーや HTTP エラー応答時は、内部詳細を伏せ、分かりやすいメッセージを画面に表示する。
- **DB障害**: Neon（PostgreSQL）への接続失敗やクエリエラー時は、サーバープロセスをクラッシュさせずに例外を捕捉し、グローバルエラーハンドラーまたはエラーレスポンスへ連携して画面にエラーを表示する。

### 4.3. 機密情報の管理

- `DATABASE_URL`、`DATABASE_URL_POOLED`、`REDIS_URL` 等の接続文字列や認証情報はコードに直書きせず、`dotenv` 等を用いてサーバー側環境変数から読み込む。
- EJS テンプレートや `public/chat/chat.js`、クライアント向けエラーメッセージに機密情報や内部接続先情報を露出させない。

### 4.4. XSS 対策

- サーバー側テンプレート（`views/chat/index.ejs`）ではエスケープ出力（`<%= ... %>`）を使用し、未エスケープ出力（`<%- ... %>`）をユーザー入力値に用いない。
- クライアント側（`public/chat/chat.js`）でユーザー名・コメント・エラーメッセージ等を DOM に反映する際は、`innerHTML` ではなく `textContent` を用いる。

### 4.5. 既存機能・共通処理の回帰確認

チャット機能追加後も、以下の既存要素が従来どおり動作することを回帰確認の対象とする。

- TOP 画面
- TODO 機能
- AI 質問機能
- 既存ルーティングおよび 404 ハンドリング
- グローバルエラーハンドリングおよび DB 接続

## 5. マルチインスタンス同期と全台合計5人制限の要件

### 5.1. メッセージ同期と全台合計5人制限の条件

- **DB 同期／ポーリング併用によるメッセージ同期**: 複数インスタンス（例: Vercel サーバーレス関数や複数コンテナ/プロセス）で稼働する場合、メッセージを Neon（PostgreSQL）に保存するとともに、クライアント側の定期ポーリング／再取得（および `Socket.IO` 配信）を併用することで、別インスタンスに接続しているクライアント間でもメッセージの整合性を保つ（要確認: ポーリング間隔の目安、および増分取得クエリ・カーソル仕様）。
- **全台合計で1ルーム5人の制限**: 定員「1部屋5人まで（セッション単位、同一ブラウザ複数タブは1名）」は単一インスタンス内だけでなく、**全インスタンスの合計同時参加セッション数**に対して適用する。インスタンスごとに個別カウントすると合計5人を超えてしまうため、共有DB（Neon PostgreSQL）等の外部状態でアクティブセッションを一元管理・判定する（要確認: ブラウザタブを閉じた際や切断・放置時のセッション解放タイミング／タイムアウト・ハートビート間隔）。

### 5.2. ローカル環境で確認する条件

- `local.ts`（またはローカル起動スクリプト）でサーバーを起動し、`/chat` にアクセスできること。
- 同一ローカルサーバー上で複数ブラウザタブ／ウィンドウおよび別セッションを開き、以下を確認できること。
  - リアルタイム送受信と `chat_messages` への保存、初期表示・再接続時の最新20件表示、ポーリング／再取得による同期。
  - 同一ブラウザの複数タブを開いた場合に1セッションとして扱われること、および別セッション5人参加中の6セッション目で満席案内と `/chat` リンクが表示され、入室・閲覧・投稿が制限されること。
  - 入力不正（空文字・空白のみ・50文字/500文字超過・型不正）、DB停止/接続エラー時の画面エラー表示とサーバー非クラッシュ。
  - 複数プロセス／ポート違い起動を用いたインスタンス間DB同期・定員共有の模擬検証（要確認: 具体的なローカル起動コマンド・スクリプト名）。

### 5.3. 複数台（マルチインスタンス）環境で確認する条件

- 複数インスタンス（または複数サーバーレス実行環境・複数コンテナ）が稼働する環境において、以下を確認できること。
  - インスタンスAに接続したクライアントの投稿が、DB保存およびポーリング／再取得（または配信経路）を通じてインスタンスBに接続したクライアントへ反映・同期されること。
  - 複数インスタンスに分散して合計5セッションが参加している状態で、別インスタンスへ6セッション目がアクセスした際も満席判定が働き、満席案内・`/chat` リンクの表示と入室・閲覧・投稿の制限が行われること。
  - インスタンスの再起動・スケールイン/アウトや一時的な切断後も、最新20件の履歴整合性と全台合計5セッションの定員整合性が保たれること。
