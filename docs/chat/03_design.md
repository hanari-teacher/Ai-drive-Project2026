## 2. アーキテクチャ責務・URL・登録順・既存処理への影響（DES-CHAT-001）

### 2.1. 各層・ファイルの責務

既存 TODO アプリ（`src/apps/todo/`）の層分離パターンを踏襲し、チャット機能の責務を次のように分離する。

* **`src/apps/chat/chatRouter.ts`（Router）**:
  * `/chat` 画面描画ルートおよび `/api/chat/*` ルートの定義とリクエスト受け渡しを行う。ビジネスロジックやSQLは持たない。

* **`src/apps/chat/chatController.ts`（Controller）**:
  * HTTPリクエストのパラメータ・ボディ抽出、入力値の基本検証呼び出し、セッション識別子の取得、参加資格／満席判定の呼び出し、JSON応答またはEJSレンダリング、および `next(err)` による共通エラーハンドラーへの委譲を行う。

* **`src/apps/chat/chatService.ts`（Service）**:
  * デフォルトルームの定員管理（最大5セッション、同一ブラウザ複数タブは1カウント）、入室・退室・席解放ロジック、メッセージ投稿の業務検証と保存・配信オーケストレーション、DB同期／ポーリング用の履歴取得・整合性制御を担う。

* **`src/apps/chat/chatModel.ts`（Model）**:
  * Neon（PostgreSQL）へのパラメータ化SQL実行（メッセージ登録、ルーム最新20件取得、ポーリング用取得、アクティブセッションの登録・更新・期限切れ回収・人数カウント）を担当する。

* **`views/chat/index.ejs`（EJSテンプレート）**:
  * チャット画面（ユーザー名入力欄・50文字上限、コメント入力欄・500文字上限、送信ボタン、メッセージ一覧領域、ステータス／エラー表示領域）および満席時の案内表示・`/chat` へのリンクを描画する。ユーザー入力値は必ず `<%= ... %>` でエスケープ出力する。

* **`public/chat/chat.js`（ブラウザJS）**:
  * `Socket.IO` クライアント制御、初期履歴・ポーリング同期・新着メッセージのIDベース統合描画、送信前バリデーション、切断・再接続制御、満席状態／通信エラー時の画面表示と `/chat` 再アクセス導線制御を担う。DOM反映は `textContent` を基本とする。

* **`sql/chat/040_create_chat_messages.sql`（SQL）**:
  * `chat_messages` テーブルおよびセッション参加管理用テーブル・インデックスのDDLを定義する。

* **`index.ts` / `local.ts`（HTTPサーバー起動箇所）**:
  * Express アプリケーションの初期化、環境変数読み込み（`dotenv`）、ミドルウェア・ルーター登録、HTTPサーバー生成と `Socket.IO` サーバーのアタッチ、および環境別（サーバーレス／ローカル）の起動処理を行う。

### 2.2. 実URLとミドルウェア・ルーター登録順

* **画面URL**: `GET /chat`（デフォルトルームのチャット画面を表示。満席時は満席案内と `/chat` へのリンクを表示）
* **API URL**: `/api/chat/*`（例: `GET /api/chat/messages`、`POST /api/chat/messages`、`POST /api/chat/join`、`POST /api/chat/leave`、`POST /api/chat/heartbeat`）
* **静的ファイルURL**: 静的アセット配信の公開パス（例: `/public/chat/chat.js` または `/chat/static/chat.js`；既存静的配信規約に合わせる。要確認事項参照）から `public/chat/chat.js` を配信する。
* **登録順と404・共通エラーハンドラーへの影響**:
  1. `dotenv` 初期化および共通ミドルウェア（JSONパーサー、Cookie／セッションミドルウェア、既存静的ファイルミドルウェア）
  2. 既存アプリルート（TOP、TODO、AI質問）
  3. チャット用静的ファイル配信および `app.use('/', chatRouter)`（`/chat` および `/api/chat/*` を処理）
  4. 既存 **404ハンドラー**（未一致パスを捕捉）
  5. 既存 **グローバルエラーハンドラー**（4引数 `(err, req, res, next)` で例外を捕捉）

* **既存機能への影響確認**:
  * チャットルートは `/chat` と `/api/chat/*` に限定するため、TOP・TODO・AI質問のパスと衝突しない。
  * 404ハンドラーはチャットルーターの後に配置されるため、存在しないチャットサブパス（例: `/chat/unknown` や `/api/chat/unknown`）は従来通り404へ流れる。
  * グローバルエラーハンドラーは末尾に維持されるため、既存機能の例外処理は変更されない。

## 3. HTTP API と Socket.IO イベント仕様（DES-CHAT-002）

### 3.1. 「接続」と「ルーム参加」の区別

* **Socket接続（Connection）**: クライアントブラウザとサーバー間のトランスポート接続確立（`connect` / `disconnect`）。未入室状態や満席状態でもHTTPリクエストやソケット接続自体は発生し得るが、それだけではチャットルームの一員とはみなさない。
* **ルーム参加（Room Participation / Admission）**: デフォルトルームの定員（最大5セッション）枠を確保し、履歴閲覧・メッセージ投稿・同ルーム配信受信の対象として承認された状態。同一セッションの複数タブは同一参加者として1枠を共有する。

### 3.2. HTTP エンドポイント一覧

対象ルームはデフォルトルーム（固定ID: `default`）のみとする。

| メソッド | パス | 参加資格・認可 | 正常応答 | エラー応答（例） |
| --- | --- | --- | --- | --- |
| `GET` | `/chat` | なし（入室判定を実施）。定員空きありで入室可、5セッション満席時は満席案内＋`/chat` リンクを表示 | `200 OK`（チャット画面HTML、または満席案内HTML） | `500` / 共通エラーハンドラー（DB障害・内部例外時） |
| `POST` | `/api/chat/join` | セッション識別子必須。満席でないこと（既存参加セッションは再入室/タブ追加として許容） | `200 OK`（`{ joined: true, roomId: "default", memberCount }`） | `409 Conflict` または `403 Forbidden`（満席時）、`400`（セッション不正）、`500`（DB障害） |
| `POST` | `/api/chat/leave` | セッション識別子必須。当該セッションのアクティブ枠を解放（他タブ有無・ポリシーに従う） | `200 OK`（`{ left: true }`） | `400`（不正入力）、`500`（DB障害） |
| `POST` | `/api/chat/heartbeat` | ルーム参加中セッションのみ。アクティブ生存時刻を更新し満席枠を維持 | `200 OK`（`{ ok: true }`） | `403 Forbidden`（未参加／満席拒否中）、`500`（DB障害） |
| `GET` | `/api/chat/messages` | **ルーム参加中セッションのみ許可**（後述の参加資格検証を実施） | `200 OK`（`{ messages: [...] }` 最新20件・古い順） | `403 Forbidden`（未参加／満席状態で履歴要求）、`400`（クエリ不正）、`500`（DB障害） |
| `POST` | `/api/chat/messages` | **ルーム参加中セッションのみ許可**＋入力検証通過 | `201 Created`（`{ message: { id, username, comment, createdAt } }`） | `400 Bad Request`（空文字・空白のみ・50/500文字超・型不正）、`403 Forbidden`（未参加／満席）、`500`（DB障害） |

### 3.3. HTTP で履歴を返す際の参加資格検証

`GET /api/chat/messages` が履歴を返す際は、以下の順序で参加資格を検証し、未達の場合は履歴を一切返さず `403 Forbidden` を返す。

1. リクエストからセッション識別子を取得する（未付与・無効形式は拒否）。
2. 共有状態（参加管理テーブル）で、当該セッションがデフォルトルームに「参加中」として登録されており、かつ有効期限（ハートビートTTL）内かを確認する。
3. 満席（5セッション到達済み）で未参加のセッションからの要求は拒否し、チャット履歴データをレスポンスに含めない。

### 3.4. Socket.IO イベント一覧

デフォルトルーム名（例: `chat:default`）を固定とし、イベントごとの送信元・受信先・payload・ack・失敗時挙動を定義する。

| イベント名 | 送信元 | 受信先 | payload | ack（確認応答） | 失敗時の挙動 |
| --- | --- | --- | --- | --- | --- |
| `chat:join` | クライアント | サーバー | `{ roomId: "default" }` | `{ ok: boolean, reason?: "FULL" \| "INVALID" \| "ERROR", messages?: Message[] }` | 満席時は `ok: false, reason: "FULL"` を返し、Socketルーム `chat:default` へ参加させずクライアントで満席案内＋`/chat` リンクを表示。 |
| `chat:message:send` | クライアント | サーバー | `{ username: string, comment: string }` | `{ ok: boolean, reason?: "VALIDATION" \| "FORBIDDEN" \| "ERROR", message?: Message, error?: string }` | 未参加・入力不正・DB保存失敗時は `ok: false` とエラー理由をackで返し、同ルームへ配信しない。クライアントはエラーを表示。 |
| `chat:message:new` | サーバー | 同一ルーム参加中クライアント（`chat:default`） | `{ id, roomId: "default", username, comment, createdAt }` | なし（クライアント側でID重複排除して描画） | サーバー側でDB保存失敗時は本イベントを発火せず、送信元ackまたはHTTPエラーで通知する。 |
| `chat:sync:request` | クライアント | サーバー | `{ afterId?: number }` | `{ ok: boolean, messages?: Message[], error?: string }` | 再接続時や同期要求時に最新20件（または指定ID以降）を返却。失敗時は `ok: false` を返しクライアントはポーリング／再取得へフォールバック。 |
| `chat:room:full` | サーバー | 満席時に入室試行したクライアント | `{ roomId: "default", message: string, retryUrl: "/chat" }` | なし | クライアントは入室・閲覧・投稿UIを制限し、満席案内と `/chat` へのリンクを表示する。 |
| `chat:error` | サーバー | 対象クライアント | `{ code: string, message: string }` | なし | クライアントはユーザー向けエラーメッセージを画面に表示する。サーバーはクラッシュさせない。 |

## 4. データベース設計・クエリ方針（DES-CHAT-003）

### 4.1. テーブル・列・型・制約・インデックス

#### (1) メッセージ保存テーブル：`chat_messages`

| 列名 | 型（PostgreSQL） | 制約 | 説明 |
| --- | --- | --- | --- |
| `id` | `BIGSERIAL`（または `BIGINT GENERATED ALWAYS AS IDENTITY`） | `PRIMARY KEY` | メッセージ一意識別子。ID統合・順序制御にも利用 |
| `room_id` | `VARCHAR(64)` | `NOT NULL DEFAULT 'default'` | ルーム識別子（初期はデフォルトルーム `'default'` 固定） |
| `username` | `VARCHAR(50)` | `NOT NULL CHECK (char_length(btrim(username)) BETWEEN 1 AND 50)` | 投稿者名（最大50文字、前後空白除去後1文字以上） |
| `comment` | `VARCHAR(500)` | `NOT NULL CHECK (char_length(btrim(comment)) BETWEEN 1 AND 500)` | コメント本文（最大500文字、前後空白除去後1文字以上） |
| `created_at` | `TIMESTAMPTZ` | `NOT NULL DEFAULT NOW()` | 作成日時（タイムゾーン付き） |

* **インデックス**:
* `CREATE INDEX idx_chat_messages_room_id_id ON chat_messages (room_id, id DESC);`
* ルームごとの最新20件抽出および `id` 基準の差分取得を高速化する。

#### (2) セッション参加管理テーブル：`chat_room_sessions`（DB同期／定員共有用）

複数インスタンス間でデフォルトルームの同時参加セッション数（最大5、同一ブラウザ複数タブは1セッション）を原子的に管理するためのテーブル。

| 列名 | 型（PostgreSQL） | 制約 | 説明 |
| --- | --- | --- | --- |
| `session_id` | `VARCHAR(128)` | `PRIMARY KEY` | セッション識別子（同一ブラウザの複数タブは同一値） |
| `room_id` | `VARCHAR(64)` | `NOT NULL DEFAULT 'default'` | 参加対象ルーム（`'default'`） |
| `connection_count` | `INTEGER` | `NOT NULL DEFAULT 1 CHECK (connection_count >= 0)` | 同一セッション内のアクティブ接続／タブ数 |
| `last_seen_at` | `TIMESTAMPTZ` | `NOT NULL DEFAULT NOW()` | 最終ハートビート／操作日時（異常終了・放置回収判定用） |
| `joined_at` | `TIMESTAMPTZ` | `NOT NULL DEFAULT NOW()` | 初回入室日時 |

* **インデックス**:
* `CREATE INDEX idx_chat_room_sessions_room_seen ON chat_room_sessions (room_id, last_seen_at);`
* 期限切れセッションの一括回収およびルーム内アクティブセッション数の集計を高速化する。

### 4.2. パラメータ化した保存・取得方針

* すべての SQL クエリはプレースホルダ（`$1, $2, ...`）を用いたパラメータ化クエリとし、文字列連結による SQL インジェクションを防止する。
* DB 接続は `DATABASE_URL` または `DATABASE_URL_POOLED` をサーバー側環境変数から取得し、共有プール経由で実行する。

### 4.3. 「最新20件を選び、その20件を古い順に表示する」クエリ方針

最新20件を確実に選んでから古い順（`id ASC` / `created_at ASC`）に並べるため、サブクエリで降順上位20件を抽出した後、外側のクエリで昇順に並べ替える。

* **取得SQLイメージ（パラメータ化）**:

```sql
SELECT id, room_id, username, comment, created_at
FROM (
  SELECT id, room_id, username, comment, created_at
  FROM chat_messages
  WHERE room_id = $1
  ORDER BY id DESC
  LIMIT 20
) AS latest_messages
ORDER BY id ASC;

```

* **表示順**: 内側で最新20件（`id DESC LIMIT 20`）を選定し、外側で `id ASC`（古いメッセージ→新しいメッセージの順）に並べ替えて返却・描画する。

## 5. ライフサイクル・同期・リスナー制御設計（DES-CHAT-004）

### 5.1. 入室から再入室までの標準シーケンス

1. **入室（Join）**:
   * クライアントが `/chat` へアクセスし、セッション単位でデフォルトルームの空き枠（現在アクティブセッション数が5未満、または自セッションが既に参加中）を確認・確保する。
   * 6セッション目以降で空きがない場合は入室を拒否し、満席案内と `/chat` へのリンクを表示する（履歴・投稿UIは非表示／無効化）。

2. **履歴取得（History Fetch）**:
   * 入室承認後、サーバーから最新20件（古い順）を取得し、画面に初期描画する。同時に DB ポーリングおよび `Socket.IO` 接続を開始する。

3. **投稿検証（Post Validation）**:
   * クライアントで入力値（型・前後空白・ユーザー名50文字以内・コメント500文字以内）を検証後、サーバー（Controller / Service）でも同一基準で再検証し、参加資格を確認する。

4. **DB保存（DB Save）**:
   * 検証を通過したメッセージをパラメータ化SQLで `chat_messages` に `INSERT` し、確定レコード（`id`, `username`, `comment`, `created_at`）を取得する。

5. **同一ルームへの配信（Broadcast to Same Room）**:
   * DB保存成功後、`Socket.IO` でデフォルトルーム（`chat:default`）へ `chat:message:new` を配信する。別インスタンスや配信取りこぼしに備え、ポーリング／再取得でも新着を取得できるようにする。

6. **切断（Disconnect）**:
   * ネットワーク断やタブクローズ等が発生した場合、クライアントは切断状態を画面に表示し、ポーリング／再接続試行を行う。サーバー側は該当接続のカウント減算または TTL 期限切れにより席回収へつなげる。

7. **再入室（Rejoin）**:
   * 再接続・再アクセス時は再度セッション単位の定員・参加状態を確認し、入室可能であれば最新20件を再取得して画面状態を同期する。

### 5.2. 履歴取得中の新着メッセージのID統合

* 初期表示や再接続時の履歴取得（`GET /api/chat/messages` または `chat:sync:request`）の最中に、リアルタイム配信（`chat:message:new`）やポーリング結果が到着する可能性がある。
* クライアントは描画済みメッセージの `id` を管理し（例: `Set` または `id -> message` マップ）、**`id` をキーに重複を排除してマージ**し、常に `id` 昇順（古い順）で描画を更新する。これにより、取得完了順の前後による二重表示や新着取りこぼしを防ぐ。

### 5.3. 切断・再接続後にイベントリスナーが増えない設計

* `public/chat/chat.js` では、ソケットインスタンス生成時またはモジュール初期化時にイベントリスナー（`connect`、`disconnect`、`connect_error`、`chat:message:new`、`chat:room:full`、`chat:error`）を **1回だけ登録** する。
* 再接続ハンドラ（`socket.on('connect', ...)`）の内部で `socket.on('chat:message:new', ...)` を呼び出さない。
* ソケットインスタンスを再生成する場合は、既存インスタンスに対して `socket.removeAllListeners()` を実行してから破棄・再作成し、リスナーの累積を防止する。

### 5.4. DB 同期／ポーリング併用の動作方針

* 書き込みの正本は Neon（PostgreSQL）の `chat_messages` とする。
* クライアントは `Socket.IO` による即時配信を受けつつ、一定間隔のポーリング（例: 数秒間隔。要確認事項参照）で最新／増分メッセージを取得し、別インスタンス経由で保存されたメッセージや取りこぼし分を同期する。

## 6. 単一／複数インスタンス参加人数管理と検証設計（DES-CHAT-005）

### 6.1. 定員ルールの定義

* 対象ルーム: デフォルトルーム（`default`）のみ。
* 上限: **最大5名（5セッション）**。
* カウント単位: **セッション単位**とし、**同一ブラウザの複数タブは1名（1セッション）** としてカウントする。6セッション目以降を満席とする。

### 6.2. 単一インスタンス時の管理

* 1プロセス起動時でも、プロセス内メモリのみではなく共有DB（`chat_room_sessions`）を基準にセッション数を集計することで、マルチインスタンス構成と同一の判定ロジックを維持する。

### 6.3. 複数インスタンス時の管理（DB 同期／ポーリング併用を採用）

* マルチインスタンス環境では `Socket.IO` のインメモリ接続数や単一プロセスの変数では全台合計5人を守れないため、**共有DB（`chat_room_sessions`）による状態管理**と**DB同期／ポーリング併用**を採用する（Redis Adapter は不採用）。

* **席の確保**:
  * 期限切れ（`last_seen_at < NOW() - interval`）の古いセッションレコードを回収したうえで、`session_id` が既に存在しアクティブであれば `connection_count = connection_count + 1`、`last_seen_at = NOW()` として枠を確保する（同一ブラウザ複数タブは既存セッション枠を利用するため人数は増えない）。
  * 新規 `session_id` の場合は、現在のアクティブセッション数が5未満であることをトランザクション／条件付き `INSERT` で原子的に確認してから登録する。5以上の場合は確保せず満席判定とする。

* **席の解放**:
  * 明示的な退出（`/api/chat/leave`）時は `connection_count` を減算し、`0` 以下になったらレコードを削除して席を解放する。

### 6.4. 異常終了時の席回収

* ブラウザの強制終了、ネットワーク切断、サーバーレスインスタンスのタイムアウト・強制終了などでは明示的退出が走らないことがある。
* 参加中クライアントは定期ハートビート（`/api/chat/heartbeat`）で `last_seen_at` を更新する。
* サーバー側は入室判定・集計・定期クリーンアップ時に、`last_seen_at` が一定時間（例: 60秒等、要確認）経過したセッションを「切断／離脱済み」とみなして削除し、席を自動回収する。

### 6.5. 障害時の扱い

* **DB接続障害／クエリエラー時**:
  * サーバープロセスは停止せず例外を捕捉し、HTTP は共通エラーハンドラー経由でエラー応答、Socket は `chat:error` / ack エラーを返す。
  * クライアントは「現在チャット機能またはデータベースに接続できません」旨のユーザー向けメッセージを表示し、不正な状態での送信や誤った満席確定を画面通知で案内する。

* **ポーリング／通信一時障害時**:* 該当回のポーリング失敗では画面全体を落とさずエラーバナー／ステータスを表示し、次回ポーリングまたは再試行操作で復帰できるよう維持する。

### 6.6. 接続先が別の2台を使う確認方法

ローカルまたはステージング環境で、**接続先（オリジン／ポート／インスタンスURL）が異なる2つのサーバーインスタンス（インスタンスA・インスタンスB）** を同一の Neon DB（`DATABASE_URL`）に向けて起動し、以下を確認する。

1. **メッセージ同期確認**:
   * クライアント1をインスタンスAの `/chat` に、クライアント2をインスタンスBの `/chat` に接続する。
   * クライアント1からメッセージを投稿し、DB保存後、クライアント2の画面にポーリング／再取得経由でメッセージが表示されること、および最新20件の順序・内容が一致することを確認する。

2. **全台合計5セッション制限確認**:
   * インスタンスAに3セッション、インスタンスBに2セッションの計5セッションを参加させる。
   * 同一ブラウザで別タブを開いた場合は合計人数が増えない（同一セッション扱い）ことを確認する。
   * 6つ目の別セッションからインスタンスAまたはBへアクセスした際、全台合計5人に達しているため満席判定となり、満席案内と `/chat` へのリンクが表示され、履歴閲覧・投稿が制限されること、および既存セッションの1つが退出／タイムアウトした後に `/chat` リンクから再入室できることを確認する。

## 7. 入力検証・XSS・機密情報・例外処理連携（DES-CHAT-006）

### 7.1. 入力検証（クライアント・サーバー二重検証）

* **型チェック**: `username` および `comment` が文字列（`typeof value === 'string'`）であることを検証する。非文字列・未定義・`null`・オブジェクト・配列は拒否する。
* **前後空白チェック**: 前後空白をトリム（`trim()`）した文字列が空文字（長さ0）の場合は不正（空文字・空白のみエラー）として拒否する。
* **文字数上限チェック**:
  * **ユーザー名**: 最大 **50文字**（51文字以上はエラー）。
  * **コメント**: 最大 **500文字**（501文字以上はエラー）。

* 検証エラー時は画面にユーザーフレンドリーなエラーメッセージを表示する。

### 7.2. XSS 対策

* **EJS テンプレート（`views/chat/index.ejs`）**: ユーザー名、コメント、エラーメッセージ、セッション表示等の動的値はすべて `<%= ... %>` で出力し、`<%- ... %>` は使用しない。
* **ブラウザ JS（`public/chat/chat.js`）**: メッセージ一覧やエラー文言を DOM へ挿入する際は `textContent` を使用し、未サニタイズの文字列を `innerHTML` に渡さない。

### 7.3. サーバー専用環境変数と機密情報管理

* `dotenv` 等を用いてサーバー起動時に環境変数（`DATABASE_URL`、`DATABASE_URL_POOLED` 等）を読み込み、ソースコードへ直書きしない。
* 環境変数やDB接続文字列はサーバー側（Model / Service / 起動スクリプト）のみで利用し、EJS レンダリング文脈、クライアントJS、APIエラーレスポンスへ一切含めない。

### 7.4. HTTP と Socket.IO の例外処理連携

* **HTTP 経路**:
  * Controller / Service / Model で発生した予期せぬ例外やDBエラーは `next(err)` へ渡し、Express の **既存のグローバルエラーハンドラー** で捕捉する。
  * グローバルエラーハンドラー側でサーバーログに詳細を記録し、クライアントには内部機密やスタックトレースを隠蔽した適切なステータス・メッセージを返す。

* **Socket.IO 経路**:
  * すべてのイベントハンドラ（`chat:join`、`chat:message:send`、`chat:sync:request` 等）を `try / catch` で囲み、未捕捉例外によるサーバークラッシュを防止する。
  * 例外発生時はサーバーログへエラー内容を出力し、呼び出し元へ ack（`{ ok: false, reason: "ERROR", error: "..." }`）または `chat:error` イベントを送信して画面にエラーを表示させる。
