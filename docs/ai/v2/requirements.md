## 1. 背景と目的

### 1.1 背景

既存のAI質問アプリ（V1）は、1問1答形式の単発質問・回答を `ai_qa_logs` テーブルに記録する構造であり、過去のやり取りを踏まえた連続的な対話や、話題ごとのスレッド管理を行うことができなかった。

### 1.2 目的

AI対話アプリ V2（以下、本システム）は、V1および既存TODOアプリに一切の悪影響を与えない独立した構成のもとで、以下の3点を実現することを目的とする。

1. **文脈を維持した連続対話:** 同一会話スレッド内の過去のやり取り（直近5往復）をAIへ引き渡し、文脈を踏まえた回答を生成する。
2. **話題ごとの会話管理・切り替え:** 新規会話の作成（タイトル入力）および一覧からの選択により、話題ごとに独立した対話空間を切り替えて利用できる。
3. **永続化と再開:** 会話およびメッセージ履歴をデータベースに保存し、ブラウザの再読み込み（リロード）後も過去の会話を選択して閲覧・再開できる。

## 2. 利用者・開始条件・対象範囲

### 2.1 利用者

* **一般利用者（受講者・アプリ利用者）:** ブラウザからV2画面にアクセスし、会話の作成、AIへの質問送信、履歴の閲覧・再開を行う。
* **授業運営者 / システム管理者:** `.env` によるモデル・APIキー設定、および公開停止（キルスイッチ）の設定・運用を行う。

### 2.2 開始条件（前提条件）

* Node.js / TypeScript (`^7.0.2`) / Express (`^5.3.0`) の実行環境が構築済みであること。
* Neon（PostgreSQL）データベースが稼働しており、既存の `db.ts`（`pool` 設定：`max: 2`, `sslmode=verify-full`）経由で接続可能であること。

* プロジェクトルートの `.env` に以下の環境変数が設定されていること。

  ```env
  GEMINI_API_KEY=<有効なAPIキー>
  GEMINI_MODEL=gemini-3.5-flash-lite
  AI_DISABLED=false
  ```

* V2用の新規データベーステーブル（会話管理・メッセージ履歴）が作成済みであること。

### 2.3 対象範囲（スコープ）

* **対象内（In-Scope）:**
  * V2フロントエンド画面（`public/ai/v2/index.html` 等）の新規作成
  * V2バックエンドAPI（`src/apps/ai/v2/`、マウントパス `/api/ai/v2`）の新規作成
  * V2用DBテーブル定義SQL（`sql/ai/` 配下）の新規作成
  * 既存 `db.ts` の `pool` の共有利用、および `index.ts` へのV2ルーターマウント追加
* **対象外（Out-of-Scope / 変更禁止領域）:**
  * V1フロントエンド（`public/ai/index.html`）およびV1バックエンド（`src/apps/ai/aiRouter.ts`、ルート `/api/ai`）の変更
  * V1用テーブル（`ai_qa_logs`）のスキーマ変更・データ変更
  * 既存TODOアプリ（`src/apps/todo/`、`src/apps/todo_v1/`、`views/todo/`、`public/todo/` および関連DBテーブル）の変更

## 5. 画面表示履歴（20往復＋20件追加）とAI送信コンテキスト（5往復）の区別

本システムでは、**「利用者が画面で確認できる履歴量（DB保存・UI表示）」**と**「AIへ文脈として送信する履歴量（APIコスト・トークン制御）」**を明確に区別して設計する。

| 比較項目 | 画面表示用履歴（UI / DB取得） | AI送信コンテキスト（Gemini API送信） |
| :--- | :--- | :--- |
| **根拠** | 授業の共通条件・確定仕様（初期20往復＋20件追加表示） | 授業の共通条件（文脈維持とAPIコスト・トークン上限のバランス） |
| **対象範囲** | 選択中の会話（`conversation_id`）に紐づく履歴 | 選択中の会話（`conversation_id`）に紐づく**直近の履歴のみ** |
| **件数基準** | ・初期表示：**最新20往復**（最大40メッセージ）<br>・追加表示：操作ごとに**20件ずつ**遡って追加取得 | ・**直近5往復**（最大10メッセージ：過去の質問5件＋回答5件）＋ 今回の新規質問1件 |
| **超過時の挙動** | DBには全件を保持し、20往復を超える過去履歴がある場合は画面に**「過去の履歴が存在します」**と表示し、追加読み込み操作で20件ずつ表示を増やす。 | 6往復以上前の履歴はDBから削除しないが、Gemini APIへのリクエスト配列には**含めない**（切り捨てる）。 |
| **データ順序** | 画面上は上から下へ古い順（時系列順）に並べて表示する。 | 時系列順（古い順→最新順）に並べた直近5往復分の末尾に今回の質問を連結して送信する。 |

## 6. データ要件・運用要件

### 6.1 データ要件

1. **1対多のデータ構造:**
   * 親テーブル（会話スレッド：`ai_v2_conversations` 等）と子テーブル（メッセージ履歴：`ai_v2_messages` 等）の1対多構造とし、外部キー（`conversation_id`）によって別会話へのデータ混入を構造的に防止する。
   * 親テーブルには、初期入力された会話タイトル（`title`）、作成日時（`created_at`）、更新日時（`updated_at`）を保持する。
   * 子テーブルには、所属会話ID（`conversation_id`）、発言者ロール（`user` / `model` 等）、本文（`content`）、作成日時（`created_at`）を保持する。
2. **DB接続プール制約の遵守:**
   * `db.ts` の接続プール上限が `max: 2` であるため、1リクエスト内で複数のDBクエリを発行する際は、コネクションの占有時間を最小限に抑え、必ず `finally` 句等でコネクションを解放（`client.release()` または `pool.query()` の単発利用）し、コネクション枯渇によるデッドロックを防止する。
3. **既存テーブルとの分離:**
   * V1の `ai_qa_logs` テーブルには一切アクセス（SELECT / INSERT / UPDATE / DELETE）しない。

### 6.2 運用要件

1. **環境変数による構成管理（`.env`）:**
   * APIキー（`GEMINI_API_KEY`）、使用モデル（`GEMINI_MODEL=gemini-3.5-flash-lite`）、公開停止フラグ（`AI_DISABLED=false`）はコード内にハードコードせず、すべて `.env` から読み込む。
2. **公開停止（キルスイッチ）運用:**
   * 授業終了後や想定外のアクセス集中・APIクォータ超過時には、管理者が `.env` の `AI_DISABLED=true` に変更してプロセスを再起動することで、即座に新規投稿（会話作成・質問送信）を停止できること。
   * UI側だけでなくバックエンドAPI側でも `AI_DISABLED === 'true'` を判定し、不正な直接APIリクエストによるAI課金・DB肥大化を確実に防ぐこと。
3. **ログ出力:**
   * エラー発生時（AI APIエラー、DB接続エラー、環境変数未設定時）はサーバーコンソールにエラー詳細（発生箇所・エラー種別）を出力し、原因調査ができること。

## 7. 未決事項・確認事項

要件定義の確定に伴い、主要な仕様（モデル名、タイトル入力方式、キルスイッチ適用範囲、20往復超過時表示）は確定済みである。詳細設計・実装フェーズに進むにあたり、以下の細部仕様について確認を要する。

| ID | 未決事項 | 確認内容・選択肢案 | 確認先 |
| :--- | :--- | :--- | :--- |
| **TBD-01** | 会話タイトルの文字数制限 | 初期入力する会話タイトルの最大文字数（例：50文字以内、100文字以内など）およびDBカラム定義（`VARCHAR(100)` 等）の基準。 | 開発担当者 / 授業担当講師 |
| **TBD-02** | 質問文（プロンプト）の文字数上限 | 1回の質問で送信可能な最大文字数（例：1,000文字または2,000文字上限）を設けるか否か。 | 開発担当者 / 授業担当講師 |
| **TBD-03** | V2画面のアクセスURLパス | 静的配信パスを `/ai/v2/`（`public/ai/v2/index.html`）としてそのまま公開する運用で問題ないか。 | プロジェクト構成規約（`index.ts`） |
